# AGENTS.md — sbe-apstore-registry

`registry.json` — единственный источник истины о том, какие SBE-плагины
существуют, где их брать (repo/branch) и какой SHA-256 у их файлов должен
быть. Читают: (1) `sbe-core/src/installer.ts` (у КАЖДОГО SBE-плагина,
клиент — планшеты/десктоп) — качает `manifest.json`/`main.js`/`styles.css`
с `raw.githubusercontent.com/<repo>/<branch>/<file>` и сверяет SHA-256 с
`hashes` из этой записи ДО записи на диск; несовпадение — install/update
прерывается с ошибкой «Контрольная сумма не совпадает». (2) ЦУП/мини-магазин
(`sbe-apstore`/`sbe-mobile`) — список доступных плагинов. Живая копия
обслуживается Caddy как статический файл `/opt/mailers/www/registry.json`
(`https://epyur.fvds.ru/registry.json`) — НЕ читается напрямую с GitHub
(во избежание 429 rate limit при частых запросах с планшетов).

## ⚠️ Обновление hashes после релиза плагина — ОБЯЗАТЕЛЬНЫЙ порядок

**Эта ошибка («Контрольная сумма не совпадает») возникала на проде УЖЕ
ДВАЖДЫ (2026-08-27, 2026-08-28) по ДВУМ РАЗНЫМ причинам — обе должны быть
закрыты, порядок ниже обязателен без исключений:**

1. **Хеши до пуша в GitHub.** Если посчитать SHA-256 от локальной сборки и
   задеплоить их в реестр ДО того, как соответствующий коммит реально
   запушен на GitHub — реестр ссылается на контент, которого там ещё нет.
   Планшет качает СТАРЫЙ файл, хеш не совпадает.
2. **CDN-задержка `raw.githubusercontent.com` ПОСЛЕ пуша** (найдено
   2026-08-28) — GitHub raw отдаётся через CDN с собственным кэшем per-file;
   `main.js` и `manifest.json` одного и того же коммита могут пропагироваться
   на разное время (наблюдалось расхождение в несколько минут между ними).
   **Один-единственный `curl` сразу после `git push` НЕ является
   доказательством того, что CDN обновился** — он мог попасть на ещё не
   обновившийся edge-узел. Проверка «попробовал разок, вроде совпало» —
   недостаточна, именно она уже привела к живой поломке обновления у
   пользователя.

**Правильная последовательность на каждый релиз плагина:**

```bash
# 1. Коммит + push плагина в его репозиторий (main/релизная ветка) — СНАЧАЛА.
git -C <plugin-repo> push origin main

# 2. Локальные хеши собранных файлов.
LOCAL_MANIFEST=$(sha256sum <plugin-repo>/manifest.json | cut -d' ' -f1)
LOCAL_MAIN=$(sha256sum <plugin-repo>/main.js | cut -d' ' -f1)

# 3. ОБЯЗАТЕЛЬНЫЙ retry-цикл против raw.githubusercontent.com — НЕ одна проверка.
#    До ~10 попыток с паузой — CDN обычно догоняет за 1-3 минуты, но может и
#    дольше; если после 10 попыток не сошлось — НЕ деплоить реестр, сообщить
#    пользователю и повторить процедуру позже (см. живой инцидент 2026-08-28,
#    где именно так и было сделано правильно, но session закончилась раньше,
#    чем CDN догнал — оставлено как pending item, а не задеплоено вслепую).
for i in $(seq 1 10); do
  REMOTE_MANIFEST=$(curl -s "https://raw.githubusercontent.com/<repo>/main/manifest.json" | sha256sum | cut -d' ' -f1)
  REMOTE_MAIN=$(curl -s "https://raw.githubusercontent.com/<repo>/main/main.js" | sha256sum | cut -d' ' -f1)
  if [ "$REMOTE_MANIFEST" = "$LOCAL_MANIFEST" ] && [ "$REMOTE_MAIN" = "$LOCAL_MAIN" ]; then
    echo "MATCH on attempt $i — safe to deploy registry"; break
  fi
  echo "attempt $i/10: raw.githubusercontent.com not yet propagated, waiting 20s..."
  sleep 20
done
# Если цикл вышел БЕЗ "MATCH" — СТОП, не переходить к шагу 4.

# 4. Только теперь — обновить hashes в registry.json (локальная копия), scp на
#    сервер (/opt/mailers/www/registry.json), подтвердить через
#    https://epyur.fvds.ru/registry.json, закоммитить/запушить сам registry-репо.
```

**Почему `raw.githubusercontent.com`, а не GitHub API/git-объекты для
проверки**: GitHub API (`api.github.com/repos/.../contents/...`) читает
напрямую из git-бэкенда и НЕ подвержен той же CDN-задержке — но именно
поэтому он НЕПРИГОДЕН как источник проверки: планшет всё равно качает файл
через `raw.githubusercontent.com` (см. `installer.ts` `rawUrl()`), значит
единственная проверка, которая реально что-то доказывает — против ТОГО ЖЕ
самого адреса, с которого качает клиент. Проверка через API даст ложное
«всё готово», пока сам raw ещё не догнал.

## Окончательное решение — РЕАЛИЗОВАНО (2026-08-29) как `selfHosted`, но с новой ловушкой

Корень проблемы — сама архитектура «раздавать файлы плагина через
`raw.githubusercontent.com`» имела присущую задержку консистентности,
которую retry-циклом можно было только смягчить. Решение, описанное здесь
раньше как «не реализовано» — раздавать файлы плагинов с ТОГО ЖЕ сервера,
что отдаёт `registry.json` (`epyur.fvds.ru/plugins/<dir>/<file>`, тот же
Caddy static file) — реализовано 2026-08-29 (`sbe-core/src/registry.ts`
`pluginFileUrl()`, ветка `if (entry.selfHosted)`) и используется через
раздел «Мои плагины» (`sbe-apstore` v0.3.13) для ручной загрузки собранных
файлов без пуша в GitHub. Дизайн-документ (восстановлен задним числом
2026-09-03, изначально отсутствовал на диске) — `docs/superpowers/specs/
2026-08-29-sbe-plugin-file-upload-design.md`.

**2026-09-03 — раскатано на весь реестр.** По требованию пользователя
(«уходим от гитхаба») все 17 записей реестра переведены на `selfHosted:
true` — не только 3, что были раньше. Файлы взяты через `git show
main:<file>` из каждого репозитория (не пересборкой — обходит и CRLF-ловушку
ниже, `git show` читает blob как есть), хеши посчитаны на сервере от
реально записанных файлов, строки в `registry_file_overrides` — batch
`INSERT ... ON CONFLICT`. GitHub-путь в коде НЕ убран — остаётся резервным
для клиентов со старым `sbe-core` (см. §5 дизайн-документа), но с этого
момента раздача файлов по умолчанию — сервер, не CDN GitHub.

**⚠️ Третий инцидент (2026-08-31) — та же ошибка «Контрольная сумма не
совпадает», третья по счёту причина:** `selfHosted` решает проблему для
клиентов с версией `sbe-core`, ЗНАЮЩЕЙ про `selfHosted` (≥ той сборки, что
загрузила это поле). Но клиент, который сам ЕЩЁ НЕ ОБНОВИЛСЯ (бандлит
старый `sbe-core`, до 2026-08-29), при самообновлении ЦУП/плагина не читает
`entry.selfHosted` вообще и всегда идёт на `raw.githubusercontent.com`.
Если после загрузки через «Мои плагины» соответствующий коммит НЕ запушен
в GitHub (или запушен, но `git` на Windows нормализовал `\r\n` → `\n` при
коммите, поменяв SHA-256 относительно того, что реально захэшировано и
загружено на самораздачу) — старый клиент качает не те байты, хеш не
сходится, апдейт падает. Обнаружено на `sbe-apstore` v0.3.14: `main.js`/
`styles.css` (эсбилд-вывод, уже LF) хешировались одинаково что на
самораздаче, что в git; `manifest.json` (правился вручную на Windows,
CRLF) — при обычном `git commit` менял хеш.

**Обязательное правило при загрузке любого `selfHosted`-плагина через «Мои
плагины»:**
1. В репозитории плагина должен быть `.gitattributes` с `-text` на все три
   файла из `INSTALL_FILES` (`manifest.json`, `main.js`, `styles.css`) —
   иначе `core.autocrlf` может незаметно поменять байты (и хеш) при
   следующем `git commit`, разойдясь с уже захэшированной самораздачей.
2. Тот же коммит, что залит на самораздачу, ОБЯЗАН быть запушен и в
   GitHub-репозиторий плагина (`git push origin main`) — иначе для клиентов
   без поддержки `selfHosted` обновление невозможно в принципе, даже без
   CRLF-проблемы.
3. Запись в ЭТОМ файле (`registry.json`, git) обновляется вместе с живым
   сервером (`selfHosted`, `hashes`, `uploadedAt`/`uploadedBy`) — иначе этот
   git-репозиторий перестаёт быть источником правды и любая будущая
   синхронизация с него на сервер откатит боевой реестр назад.

Затрагивает `installer.ts`/`registry.ts` — общий код ДЛЯ ВСЕХ SBE-плагинов;
проверить `.gitattributes` стоит для каждого репозитория, который когда-либо
будет загружен через «Мои плагины».
